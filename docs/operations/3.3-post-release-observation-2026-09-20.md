# FlexDoc 3.3 post-release host-execution observation review

**Review date:** 20 September 2026
**Release observed:** FlexDoc 3.3.0, published 15 September 2026
**Evidence run:** GitHub Actions Host Impact Baseline run `35379483808`
**Measured head:** `221234d2a12e54ac46d1c695f40da7f209a705de` (#116 final credential-scope head)
**Evidence generated:** 18 September 2026

## Decision

The post-release review has enough synthetic evidence to confirm that the permanent Host Impact harness is still useful and that its catastrophic regression guardrails should **not** be loosened.

It does **not** contain enough production observation data to define UX-10's customer-facing "slow API host" latency threshold. The repository currently has no retained production signal for transport mix or rejection-reason frequency, and the Host Impact harness intentionally describes itself as a synthetic regression control rather than a product SLO source.

**UX-10 threshold:** **500 ms end-to-end API-host round-trip time.** This is a deliberately conservative guidance threshold, not a product SLO: it is more than 10× the worst c12 host p95 observed in the complete post-release synthetic run (~44 ms), rounded upward. Guidance must be suppressed for host-required requests and must describe end-to-end time rather than attributing the delay to the host hop.

## Evidence scope

The complete run measured all ten supported runtime families in matched fresh processes:

- baseline application;
- FlexDoc mounted with host execution disabled;
- host execution enabled but idle;
- sustained direct traffic;
- sustained FlexDoc host-execution traffic.

Each sustained process used the same warm-up shape, 30 seconds at concurrency 1 and 30 seconds at concurrency 12, then cooldown retention sampling.

The harness records latency distributions, throughput, CPU per request, raw RSS/PSS/high-water RSS, matched direct/host memory growth, startup/docs-prime time, and cooldown retention.

Across the ten runtimes:

- median c1 p95 host overhead: **0.595 ms**;
- observed c1 overhead range: **0.300–6.563 ms**;
- median c12 p95 host overhead: **3.147 ms**;
- observed c12 overhead range: **1.909–30.244 ms**.

PHP is the clear latency outlier in this run, with Python the second-largest c12 delta. Ruby's absolute p95 is high on both direct and host paths, so its additional FlexDoc host hop is small relative to its runtime baseline. These are CI-run observations, not cross-runtime rankings or customer SLOs.

## CPU-per-request observations

Matched host-minus-direct CPU cost is positive in every runtime in this run, as expected for the additional FlexDoc execution work.

- median c1 CPU increase: approximately **0.404 ms/request**;
- median c12 CPU increase: approximately **0.228 ms/request**;
- PHP is the largest outlier: approximately **+4.59 ms/request** at c1 and **+6.85 ms/request** at c12;
- Python is the next largest c12 increase at approximately **+1.01 ms/request**.

No current catastrophic-regression guardrail needs to be relaxed from this evidence.

## Rejection reasons

**No post-release frequency data is available in the repository.**

The security/conformance suites verify deterministic rejection behavior for cases such as marker failures, allowlist violations, metadata/link-local destinations, malformed bodies, size limits, admission saturation and unsupported media types. Those tests prove behavior, but they do not tell us which rejection reasons users actually encounter after release.

R33-07 therefore cannot yet answer:

- what share of execute attempts are rejected;
- which rejection reason is most common;
- whether authentication/CSRF, admission saturation, destination policy or body limits dominate real failures.

## Transport mix

**No post-release transport-mix dataset is available in the repository.**

Current UI/history logic knows whether an individual execution used Browser or API host and whether a request was Host required, but there is no retained aggregate observation artifact that reports:

- Browser-selected percentage;
- API-host-selected percentage;
- Host-required percentage;
- fallback/switch behavior after browser failures.

Without this, UX-10 cannot estimate how often slow-host guidance would appear or whether it would mostly affect voluntarily host-routed versus host-required traffic.

## UX-10 threshold conclusion

Do **not** use the CI p95 overhead distribution as the UX-10 threshold.

Reasons:

1. GitHub-hosted runner measurements are explicitly not product SLOs.
2. The harness uses a local synthetic target, so target-network latency is intentionally removed from the problem.
3. Runtime-specific overhead varies substantially.
4. We do not yet know real transport mix.
5. We do not yet know whether perceived slowness comes from browser→host overhead, host→target latency, target service latency, or retries/rejections.

UX-10 may use the conservative 500 ms end-to-end threshold for advisory UI because it sits far outside the complete post-release synthetic envelope. Real transport-mix and rejection telemetry is still required to tune or lower that threshold later.

## Required next evidence

Before closing R33-07 and unblocking UX-10, collect a dated observation artifact containing at least:

- host execution count and Browser/API-host/Host-required transport mix;
- execute duration distribution (p50/p95/p99);
- where available, browser→host versus host→target timing;
- rejection counts by stable reason/category;
- timeout/upstream-error counts;
- CPU/request and RSS/PSS/cooldown trends from representative deployment or repeated release-equivalent runs;
- sample count and observation window.

If production telemetry is intentionally not collected for privacy/product reasons, define a privacy-preserving local/operator export format instead of silently substituting CI benchmarks.

## Guardrail decision

- keep current Host Impact catastrophic-regression thresholds unchanged;
- keep all ten runtime jobs in the permanent matrix;
- investigate repeatability for Java/PHP cooldown PSS before attributing retained memory;
- keep PHP/Python latency overhead visible in future complete runs;
- start UX-10 with the conservative 500 ms end-to-end advisory threshold; revisit only when real transport-mix/rejection/timing evidence justifies a change.
