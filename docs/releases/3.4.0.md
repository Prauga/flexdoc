# FlexDoc package release 3.4.0

FlexDoc **3.4.0** is the JavaScript package version that publishes the completed 3.3.x hardening line. Package semver and internal product-milestone labels are independent from this release onward.

## Package versions

The coordinated JavaScript packages move together:

- `@prauga/flexdoc-client` — **3.4.0**
- `@prauga/flexdoc-backend` — **3.4.0**

Native ecosystems keep independent semver and publish the OBS-07 evidence work on their own feature-minor lines:

- Python `prauga-flexdoc` — **0.9.0**
- Java/JVM/JAX-RS/Spring family — **0.10.0**
- .NET `Prauga.FlexDoc.AspNetCore` — **0.7.0**

`@prauga/flexdoc-core` and `@prauga/flexdoc-cli` are unchanged because this wave does not modify them.

## Multi-instance host execution

MI-01 through MI-06 make horizontally scaled Node deployments an explicit supported configuration instead of a process-local accident:

- operators may inject one shared `sessionSecret`;
- `sessionStore` provides an async application-owned read/write/clear contract while preserving the in-process default for single-instance use;
- declaring `instances: 'multiple'` without both shared pieces withholds the `cookies` capability instead of silently resetting jars;
- `fleetMaxInFlight` is partitioned statically across the declared instance count, avoiding a network dependency in the admission decision;
- per-instance observation documents can be merged into `flexdoc.host-execution.fleet-observation/1` with exact additive counts, explicit concurrency bounds, and no fabricated cross-instance percentiles;
- Compose, Kubernetes and plain load-balanced deployment guidance documents authentication -> CSRF/same-origin -> admission -> FlexDoc ordering, secret distribution, fixed replica arithmetic and the session-affinity interim.

Shared cookie-jar stores contain third-party session credentials. The deployment contract therefore calls for short TTLs, the backing store's normal encryption-at-rest controls, and no logging or telemetry of serialized cookie values.

## Uniform execution evidence

OBS-07 extends the execution-evidence contract to every runtime serving the native execute route. Node, Python, Go, Rust, Ruby, PHP, Elixir, .NET and Java now use the same thirteen-value reason vocabulary, metric names and `flexdoc.host-execution.observation/1` export shape.

Two invariants are part of that contract:

- a metric sink failure is swallowed so observability cannot decide whether execution succeeds;
- when a throw site does not provide a more specific reason, the reason defaults from HTTP status so new rejection paths cannot silently fall out of the evidence vocabulary.

## JavaScript API note

`runHostCookiesRoute` now returns `Promise<HostExecutionRouteResult>` because a configured session store may perform remote I/O. Direct callers of this low-level export must await it.

All in-repository callers already run inside async handlers and await the result, and the function was not documented as an application integration API. The affected compatibility surface is therefore external direct callers of an undocumented low-level export; this is a changelog-level API note rather than a migration program.

## Release sequencing

This wave used the version contract's in-flight window. Examples and install documentation stayed pinned to the previously published artifacts while source versions sat in `pending`. After the registry artifacts existed, the follow-up repin updated examples, generated lock and checksum metadata and the published baselines, then cleared `pending`. That window is closed for 3.4.0.

For Rust, `rust-host/v0.2.0` published before the Axum and Actix releases because both adapter crates depend on that shared crate. The same order applies to any later release of those crates.
