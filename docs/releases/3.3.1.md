# FlexDoc 3.3.1

Published maintenance release. The Java **0.9.0** and ASP.NET Core **0.6.0** artifacts named below are on their registries.

FlexDoc 3.3.1 hardens backend-native host execution without changing the 3.3 transport contract. The primary change is HX-03 protection parity: runtimes that can expose a real host executor now require an explicit acknowledgement that the application already protects the documentation and execute surface with its own authentication/authorization boundary.

## Host-execution protection parity

The following source releases carry the new fail-closed acknowledgement:

- Java JVM / JAX-RS / Spring family: **0.9.0**
- ASP.NET Core: **0.6.0**

The minor bumps were intentional because the adapters add a new required configuration acknowledgement when a real host executor is exposed. Both artifacts published with this release.

### Java

Configure the actual application security boundary first, then set `hostExecutionProtected(true)` (or the Spring property equivalent) before attaching a real host executor. A real executor without that acknowledgement is rejected during initialization. Advertising host-execution protocol metadata without an executor can still remain unavailable without the acknowledgement.

### ASP.NET Core

Configure the application authorization boundary for the docs shell/subtree first, then set `HostExecutionProtected = true` before attaching a real `FlexDocHostExecution`. `MapFlexDoc` rejects a real executor when the acknowledgement is missing.

## Security semantics

The acknowledgement is not authentication, authorization, or CSRF protection. Exact-origin allowlists and `X-FlexDoc-Execute: 1` remain execution controls only. Operators must protect the docs and execute route with the application's normal access-control boundary.

## Compatibility

The browser/host execution envelope and 3.3 renderer contract remain unchanged. This maintenance release only closes the remaining initialization-time protection gaps for the Java and ASP.NET Core adapters.
