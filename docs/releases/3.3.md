# FlexDoc 3.3

FlexDoc 3.3 moves ordinary interactive API Client execution onto the API host when a serving adapter advertises a real native host executor. The renderer and API Client state model remain shared; the change is in the network transport used for a resolved request.

## Package versions

The JavaScript product packages follow the FlexDoc product release line:

- `@prauga/flexdoc-client` — **3.3.0**
- `@prauga/flexdoc-backend` — **3.3.0**

Native adapters are published on independent ecosystem-specific 0.x version tracks rather than being artificially renumbered to match the product release. The 3.3 source tree contains the host-execution contract in:

- Python `prauga-flexdoc` 0.7.2
- Java reactor / JVM / JAX-RS / Spring family 0.8.2
- .NET `Prauga.FlexDoc.AspNetCore` 0.5.2
- Rust Axum `prauga-flexdoc-axum` 0.5.4
- Rust Actix `prauga-flexdoc-actix` 0.4.4
- Ruby `prauga-flexdoc` 0.4.4
- Elixir `prauga_flexdoc` 0.4.4
- PHP `prauga/flexdoc` 0.4.4
- Go `github.com/prauga/flexdoc/adapters/go` source/tag version 0.5.4

This independent-version policy is deliberate: the product release identifies the compatible source/contract set, while each native package preserves its existing semver history.

## Native execute routes

When explicitly enabled and configured with an exact-origin allowlist, the native Spring, JAX-RS, FastAPI/ASGI, Go, ASP.NET Core, Axum, Actix, Rack/Rails, Plug/Phoenix, Laravel and Symfony integrations can own:

```text
POST <docsPath>/__flexdoc/execute
X-FlexDoc-Execute: 1
```

The marker is protocol/cross-site friction only. It is **not authentication and is not a CSRF token**. Protect the docs subtree and execute endpoint with the same application authentication/authorization policy as any other privileged developer surface.

## `preferHostExecution` and `capabilities: []`

For interactive browser API Client sends, host execution is preferred by default when `hostExecution.available` is true. This is true even when the host advertises `capabilities: []`.

An empty capability list means **basic native host transport is available, but advanced host-only features are not**. It does not mean host execution is disabled. Cookie jars, client certificates, Digest, Hawk, OAuth 1.0 and SigV4 remain fail-closed unless a host explicitly advertises those capabilities.

Reusable collection/headless execution intentionally keeps direct transport as its default unless the caller explicitly opts into host execution or a requested feature requires host semantics. This interactive/headless divergence is deliberate: interactive documentation benefits from the API host's network reach by default, while reusable automation does not silently move network origin.

## Operational change: traffic now reaches the API host

When host execution is available, an ordinary interactive send incurs an additional browser → API-host hop before the API host connects to the target. Expect some additional latency compared with direct browser fetch, and account for the execute traffic as real load on the docs/API host.

Enabling host execution also grants authenticated documentation users controlled outbound egress from the API host's network context. Exact-origin allowlists, metadata/link-local blocking, DNS/address pinning and redirect revalidation constrain *where* requests can go; they do not limit *how many* requests a valid user can cause.

Production deployments should therefore add operator-level abuse controls appropriate to the application, such as:

- authentication/authorization on `/docs/**` and the execute POST;
- per-user/session or reverse-proxy rate limits;
- bounded concurrent execute requests;
- upstream/gateway request-body and timeout limits;
- monitoring/alerting for execute QPS, rejection rate and target latency.

See [`docs/host-execution-operations.md`](../host-execution-operations.md) for the canonical operations guidance and concrete Node/Express and Spring admission-control patterns.

## CSRF and framework middleware

If authentication is cookie based, apply the application's normal CSRF model. `X-FlexDoc-Execute: 1` does not replace it.

- Spring: keep the docs/execute path behind Spring Security or the deployment gateway and configure CSRF deliberately for the API Client POST.
- Laravel: host execution requires configured application middleware; do not expose the execute route with an empty middleware stack.
- Symfony: configure firewall/access-control rules for both `/docs/**` and `POST /docs/__flexdoc/execute`.
- Other native adapters: mount the docs and execute route inside the same authenticated router/middleware boundary.

## Security model

Native 3.3 transports use exact-origin allowlists, block link-local/cloud-metadata destinations, revalidate same-origin redirects, validate and pin DNS/address sets where supported, preserve original Host/SNI/TLS authority, reject unsafe transport headers, enforce bounded request/response sizes and apply execution deadlines. System proxy routing is bypassed by native pinned transports so proxy configuration cannot silently bypass destination validation.

## Performance and monitoring

The repository includes a permanent ten-runtime host-impact workflow with matched direct-versus-host traffic controls, RSS/PSS, latency, throughput, CPU/request and cooldown retention. Managed-runtime PSS attribution is treated as directional investigation context rather than live-object accounting; suspicious JVM/.NET values require repeat runs plus heap/native evidence before being called retained FlexDoc memory.
